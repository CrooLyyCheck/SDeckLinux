# Marketplace OAuth routing failure

The user completed and approved browser dispatch, but the original application
did not become logged in. This was a failed real test, not an unperformed test.

## Observations

- The original process remained in the audited prefix throughout.
- At 22:39:12 and 22:59:57 (Europe/Warsaw), the app started Marketplace OAuth.
- After browser approval, app receipts at 22:39:27, 22:50:22 and 23:00:10 were
  `streamdeck://open/mainwindow`, without OAuth query parameters. The old
  `streamdeck-wine` launcher logs and journal entries accompanied those receipts.
- The screenshot and user confirmation established that browser approval was
  performed. Do not request that same test again without a concrete deployed fix.
- The MIME default was already `io.deckbridge.UrlHandler.desktop`.
- The portal's remembered entry was independently
  `desktop-used-apps / x-scheme-handler/streamdeck`, caller ID `""`, value
  `["streamdeck-wine", "2", "3"]`, data variant byte zero.
- The old launcher's desktop entry has no `%u`/`%U`; the new handler does.

Official portal 1.22.1 source explains the discrepancy: a sole recommended choice
can skip the chooser, after which the remembered handler is selected for custom
schemes. Thus the browser dialog's MIME-derived name could show DeckBridge while
the portal still launched the old application.

## Privacy-preserving diagnosis

Only fixed route classes, parameter-presence booleans, timestamps and component
names were emitted from app logs. No real code, state value or token was printed.
A locked browser history database was inspected through a bounded 4.9 MB private
temporary snapshot with a consistency check, restricted query and immediate
deletion. It established that the authorization-code/PKCE request used the
official Elgato external redirect service. No browsing records were retained.

The public redirect service was tested with **synthetic values only**. It emits
`streamdeck://marketplace/auth` with `code` and `state`; its landing-page retrieval
is single-use (a second synthetic read returned 404). Do not reuse a previous
landing page or replay authorization codes to compensate for a lost callback.

## Fix and evidence

The installer now backs up remembered legacy choices in its private manifest,
then changes only their handler ID to `io.deckbridge.UrlHandler` using
`PermissionStore.SetPermission`. It retains `2,3`, other application choices and
the data variant. No browser consent setting, global security setting or Wine
prefix file is modified.

An actual `org.freedesktop.portal.OpenURI.OpenURI` test delivered a synthetic
Marketplace callback into Elgato's `EGMPOAuthExternalReplyServer::handleMessage`
in the same original process. It produced the expected rejection for a synthetic
state and did not invoke the legacy launcher. This proves repaired routing into
the authentication consumer, not successful token exchange or account linking.

`deckbridge diagnose` now reports both the MIME handler and portal handler;
structured request logs distinguish actions from diagnostics while omitting
payloads and client-supplied IDs. Installer tests cover restoring previous portal
choices and preserving subsequent user choices.

## Acceptance still required

A fresh login begun in the original application after this fix must link the
account. A clear **test now** signal was given and a payload-free live observer
started; leave the service unchanged during that attempt. Never infer OAuth
success from a launched process, browser approval alone or synthetic rejection.
